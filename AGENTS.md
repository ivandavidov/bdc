# AGENTS.md

Насоки за AI агенти и разработчици, които работят по BDC Радар. Какво е проектът и как се пуска е описано в [README.md](README.md).

## Накратко

- Python pipeline (`pipeline/`) събира публични данни (SEC EDGAR, Yahoo Finance), смята метрики и скор и записва JSON в `docs/data/`.
- Статичен сайт (`docs/`) чете тези JSON файлове. Няма build стъпка, npm или framework: чисти HTML страници и ES модули.
- GitHub Actions пуска pipeline-а всеки делничен ден и commit-ва данните. Сайтът се публикува от `docs/` чрез GitHub Pages.

## Команди

```bash
uv venv -p 3.12 .venv && uv pip install -p .venv -r requirements.txt   # среда (Python 3.10+)
.venv/bin/python -m pytest -q                                          # тестове — пускай ги преди всеки commit
.venv/bin/python -m pipeline.build                                     # пълно изграждане (нужен е SEC_USER_AGENT)
.venv/bin/python -m pipeline.build --skip-universe --only ARCC MAIN    # бързо, само за няколко тикера
.venv/bin/python -m pipeline.report                                    # отчет за качеството на данните
python3 -m http.server 8000 --directory docs                           # преглед на сайта
```

- `SEC_USER_AGENT` е задължителен за заявки към SEC (`"bdc-radar email@example.com"`). Не го commit-вай.
- Пълното изграждане е бавно първия път (~20–30 мин). После ползва кеша в `data_cache/`, който не е в git.

## Поток на данните

`build.py`: universe → за всяка компания (`facts` → `prices`/`dividends` → `metrics` → `holders`) → `portfolio.attach` → `scoring.score_all` → `sector()` (медиани + `health.build`) → `scoring.attach_percentiles` → `events.update` → запис.

| Файл | Съдържание |
|---|---|
| `docs/data/summary.json` | Ред за всяка компания: полетата от `SUMMARY_FIELDS` + скор, светофар, флагове |
| `docs/data/companies/<TICKER>.json` | Всичко за една компания: тримесечни серии `q`, седмични цени, дивиденти, портфейл, акционери, скор, персентили |
| `docs/data/sector.json` | Секторни медиани по календарни тримесечия, седмичен P/NAV, `health` (претеглени агрегати и общи non-accruals) |
| `docs/data/meta.json` | Дата на генериране и публичната методология от `config/scoring.yaml` |
| `docs/data/events.json`, `docs/feed.xml` | Дневник на промените и RSS |

## Правила

### Данни
- **Не редактирай на ръка `docs/data/` и `docs/feed.xml`.** Генерират се от pipeline-а и ботът ги презаписва всеки ден.
- Ако промяна в изчисленията на сектора трябва да се види веднага, без пълно изграждане, `build.sector()` може да се пусне върху вече записаните `docs/data/companies/*.json`. Те съдържат всичко нужно. Ако не, остави данните да се обновят при следващото дневно пускане.
- Ботът commit-ва в `main` всеки делничен ден. Преди push направи `git pull --rebase`. При конфликт в `docs/data/` вземи версията от `origin`; данните се генерират наново.
- Липсваща стойност е `None`/`null` и в UI се показва като „—“. Никога не замествай липсваща стойност с 0.
- Съотношенията се пазят като дроби (0.035 = 3.5%). Форматирането е само в UI.
- Тримесечията на компаниите са по края на отчетния период. За секторни агрегати те се групират по календарно тримесечие (`2026Q2`).

### Методология
- Скорът, теглата, праговете и флаговете живеят само в `config/scoring.yaml`. Страницата „Методология“ се рисува от тях чрез `meta.json`, затова не дублирай числа в HTML.
- Промяна в методологията е видима за потребителите. Обнови коментарите в `scoring.yaml`, тестовете в `tests/test_scoring.py` и при нужда текста в `docs/methodology.html`.
- Нова метрика минава през няколко места: изчисление в `metrics.py` (или `portfolio.py`) → `SUMMARY_FIELDS` в `build.py`, ако трябва в таблицата → `DIRECTION` в `scoring.py`, ако има персентил → `scoring.yaml`, ако влиза в скора → `METRICS` в `docs/assets/js/metrics-def.js` (етикет, формат, посока, обяснение).

### Frontend
- Без build инструменти и нови зависимости. Единствената външна библиотека е ECharts 5.6.0 от jsDelivr.
- Графиките минават през обвивките в `charts.js` (`line`, `bars`, `hbars`, `scatter`). Под всяка графика добавяй `dataTable` за достъпност.
- Числата и датите се форматират само чрез `format.js` (bg-BG: запетая за десетични, `—` за липса).
- Цветовете са CSS токени в `style.css` с варианти за светла и тъмна тема. Не пиши цветове директно в JS или HTML.
- `localStorage` се ползва само чрез `store.js` (всеки достъп е в try/catch).
- Страницата трябва да работи на телефон (375px) без хоризонтално превъртане на цялата страница.

### Език и стил
- Целият текст в сайта е на **български**, ясен за непрофесионален инвеститор. Финансовите термини без утвърден превод остават на английски (NAV, NII, PIK, non-accruals) и се обясняват в речника.
- Python: docstrings и коментари на английски, `from __future__ import annotations`, типови анотации, малки чисти функции.
- JavaScript: коментари на български, както в съществуващия код.
- Съобщенията на commit-ите са на български, едно изречение за това какво се променя.
- Предупреждението „Това не е инвестиционен съвет“ трябва да остане в сайта и в README.

### Тестове
- Тестовете в `tests/` не правят мрежови заявки. Ползвай малки ръчно написани входни данни, както в `tests/test_health.py` и `tests/test_portfolio_metrics.py`.
- Всяка нова логика за изчисление в `pipeline/` трябва да има тест.
- При промяна във frontend-а пусни локалния сървър и провери страницата в браузъра: конзолата да е без грешки, а светлата/тъмната тема и мобилният изглед да са наред.

## Капани

- XBRL таговете се различават между компаниите. Ако метрика липсва при някой BDC, добави кандидат-таг в `config/xbrl_tags.yaml` вместо специален случай в кода.
- Много 10-Q отчети съдържат само суми от началото на годината. `facts.py` изважда предишния период, така че не събирай тримесечия наивно.
- Сумите от Schedule of Investments понякога не отговарят на баланса. Затова `portfolio.py` маркира портфейла като `reliable` само при покритие 60–125%; ненадеждните стойности не влизат в скора.
- Имената в списъците с non-accruals често съдържат индустрия, тип заем и дати. `health.core_name()` извлича самото име; пази тестовете му, ако го пипаш.
- `yfinance` е неофициално API и понякога се чупи. Кодът пада обратно към последния кеш, така че не прави изграждането зависимо от успешно сваляне.
